# 项目任务与提交流程

供筹备、编辑与项目维护使用。按任务读对应小节，正文写手读 [writer-context.md](writer-context.md)；不把本文整份作为写作提示。

## 选择轻流程或正式流程

先按用户要求确定交付范围。试写、审读、局部修改候选使用轻流程；明确要建立持续项目、继续正式连载或采用候选入库时使用正式流程。用户已有授权直接沿用，不要求重新确认一次。

### 轻流程：试写、审读与修改候选

1. 读取用户提供的正文、目标、风格和必要前后文；缺少影响本次结果的关键信息才询问。试写可使用暂定人物和书名，不先做市场、包装、角色意图 JSON 或项目初始化。
2. 按本次范围直接写作、审读或局部修改。候选放在用户指定位置；已有正式项目时默认放 `drafts/`，不覆盖 `chapters/`，不更新正史、正式章号或完成字数。用户直接要求修正正式文件时按正式流程处理。
3. 检查本次目标、事实与指代、必要接续及原有声音。长篇试写按实际需要使用切章工具；没有具体问题就保留原文。轻流程不要求生成三份审稿 JSON 或模拟多轮审稿，不能宣称已经通过正式门禁。
4. 交付正文或候选与必要说明。用户要采用入库时，复用有效候选，执行完整审稿和提交事务；不因进入正式流程重新生成已认可正文。轻流程不能用来规避正式入库校验。

### 正式入库与发布准备

正式入库执行下文的项目、审稿、正史和提交规则。发布包装按用户需求另行开展：可以用暂定书名写作并让 `publishingPackage` 保持 `unconfirmed`，校验会提示未完成包装。没有完成检索、封面或作者确认时如实保留未完成状态。

发布前再按 [publishing-package.md](publishing-package.md) 确认书名、简介、公开检索和封面。仅请求书名或封面时只处理对应部分；完整包装尚未完成时不标记 `active`。书名与正文承诺不一致时先核对原因，不擅改已确认故事方向。

## 新建项目

1. 若用户未指定项目路径，在当前工作目录下使用安全的作品名创建项目文件夹。
2. 只询问无法合理推断且会改变作品方向的信息。通常一次收集：故事种子、希望避免的内容、主角初始困境。题材可以由故事种子推导，也可以给出 3 个差异明显的方案让作者选择。
3. 确认 `serial`、`fanqie-short-story` 或 `novella`，提出简短的故事合同，并按 [style-system.md](style-system.md) 给出 2–4 个适配的语言风格选项。用户指定作者时先做手法转译卡；用户提供亲手改稿或原创样本时，按 [prose-naturalization.md](prose-naturalization.md) 提取有逐字证据的个人声音规则。短故事还需确认目标总长度、预计分节和结尾类型；短中篇确认全书目标、明确下限（若有）、结局选择与代价、人物归宿及必要副线，不预设必须写满的章数。
4. 用户要求市场定位或题材竞争不明时，按 [market-research.md](market-research.md) 研究公开来源；正式建项前先把快照保存在项目外的临时工作目录，不能成为迟迟不写的借口。短故事必须以短故事专属样本为主要证据，长篇榜只能作为旁证，不能据此宣称短故事热门。新书设定按 [fanqie-new-book.md](fanqie-new-book.md) 核对：有先例就要写出可观察的微创新，读者不能预判后文每一拍。
5. 用户同时要求发布包装时，按 [publishing-package.md](publishing-package.md) 生成适量候选书名（可参考 8–12 个），筛出 3 个做公开精确检索；为推荐书名提供封面主提示词、负面提示词，并按 [cover-typography.md](cover-typography.md) 给出 3 个结构明显不同的书名字效方向，推荐其中 1 个，写清断行、字形骨架、笔画性格、材质、描边层、投影/立体深度、占比、安全区和主体遮挡关系。将候选合同或项目运行 `story_overlap.py`，与作者同一作品库中的历史项目比较；高风险时重做人物、关系、核心危机或解决机制，除非作者确认是同世界观续作。
6. 对齐故事合同、第一卷重大设计和语言风格；已有授权直接沿用。终选书名、简介和封面仅在本次处理包装时一并确认。卷纲先写卷末不可逆状态差，再倒推必须先发生的选择；有金手指时先回答 [continuation-engine.md](continuation-engine.md) 的四问。不要在确认前批量写正文。
7. 运行：

```bash
python3 <skill-dir>/scripts/init_project.py --path <项目目录> --title <书名> --style <风格标识> --mode <模式> --protagonist-id <id> --protagonist-name <姓名>
```

8. 本次完成整套发布包装时，用 `publishing_package.py` 保存公开检索记录与封面提示词；否则保留 `publishingPackage.status = unconfirmed`。若第 4 步生成了市场快照，用 `market_brief.py` 归档到项目。将确认内容和已作出的重大选择写入故事合同及决策记录，建立主要人物、分层配角、世界规则与 `canon/laws.md`，填主角 `cast/{id}/SKILL.md` 和 `planning/current-arc.md`。长篇规划当前卷和接下来几个事件，约5–10章只作工作量估计，不分派各章剧情；短故事按 [length-modes.md](length-modes.md) 规划全文剩余分节。
9. 运行 `plan_cadence.py --write`。长篇只记下贯穿线的兑现间隔，不按章号预写未来 15 章的情节或兑现；短故事按预计总分节建立全文比例结构锚点。补全每个锚点的回报类型、铺垫和代价。
10. 运行 `validate_project.py`。正式入库前确认故事方向与语言风格；未完成包装和市场研究不阻断正文入库。

`novella` 建项使用 `--mode novella --target-total-chars 50000`，可按作者下限另加 `--min-total-chars`；不传 `--sections`。第 6–9 步改用全书终点、必要副线与剩余阶段规划，`plan_cadence.py` 只展示阶段职责，不预写章号锚点或 15 章节拍。结局、语言风格与故事合同仍需确认。

## 参考短故事再创作

把“仿写”解释为复用阅读机制，不解释为换名复述。先从参考稿提取抽象机制卡和必须替换清单，再只依据机制卡设计新故事合同；人物专名、独特物件、事件链、证据链、关键场面、结局揭示和标志性表达不得沿用。参考稿属于作者本人或公版且作者明确要求改编时，才按其确认的授权范围保留具体元素。

写正文时不要逐段对照参考稿。每节完成后运行 `reference_guard.py` 检查连续原文复用与禁用词，再运行 `story_overlap.py` 检查作者作品库内的同质化；任一高风险都先重写，不能把脚本结论称为抄袭认定或法律判断。

### 番茄短故事差异

- 一个短故事是一个有终点的作品，不是缩短版无限连载。只保留一个主承诺、一个主要矛盾和能在结局前闭合的少量副线。
- 短故事若采用规则反噬型现实爽文，必须走“真实让步 → 规则/权势反咬 → 主角合法收回人情 → 依赖关系瓦解 → 对方按自己的逻辑承受后果”的因果链；写前卡补充 `goodwillGiven`、`betrayalMechanism`、`lawfulExit`、`dependencyChain`，报应若与前面建立的依赖无关，视为假反转。详见 [length-modes.md](length-modes.md) 的“规则反噬型现实爽文”。
- 短故事必须有情绪曲线：建项时确定一个主情绪发动机；每节写明进入情绪、方向变化、具体代价和离场余波。至少一次让希望被事实打断、至少一次让主角为主动选择付出不可撤回的损失，最后用行动释放情绪。连续三节情绪方向和强度没有变化，或只能用“很生气/很难过/更紧张”概括，先重排章纲再写正文。具体格式见 [length-modes.md](length-modes.md) 的“情绪曲线”。
- 正文可以是一个完整文本或少量连续分节；每节仍执行指标、语言扫描、编辑审稿、读者模拟和状态提交。分节不是事件结案单位：先标记事件线 ID、`opening`/`middle`/`turn`/`closing` 阶段和本节局部交付，前面阶段允许把行动和答案交给下一节。
- 短故事动笔前建立入口合同；标题、前 300 字、主情绪发动机、情绪波形、主动选择和试读节点按 [short-story-information-flow.md](short-story-information-flow.md)、[fanqie-new-book.md](fanqie-new-book.md) 与 [length-modes.md](length-modes.md) 联动检查。前 300 字必须让冷读者说清“谁遇到什么、做了什么、会失去什么、接下来等哪个答案”，但不按固定句数或反转次数机械写作。
- 把 `shortStory.status` 从 `planning` 更新为 `drafting` 后再提交第一节。全文终审通过、主要线索闭合且结局回报已交付后改为 `complete`。
- 标记 `complete` 后停止自动续写。改成长篇、增加续作或重开结局都必须询问作者。
- 短故事进入 `complete` 前必须完成全文外部读者终审，写入 `reviews/final-review.json`；这里的“第三视角”指作者退场的普通读者审读，不改变正文既定人称。终审收口必须主承诺兑现且最后一场动作做完，细则见 [fanqie-signing-quality.md](fanqie-signing-quality.md)。人物选择一致性、胜利代价、情绪身体反应与对白辨识见 [fanqie-character-craft.md](fanqie-character-craft.md)。
- 发布后不要从一次小流量测试反推永久结论。保存推荐状态和完整漏斗数据；下一个故事的选题与包装可以吸收数据，但不能把无样本的猜测写成平台规则。

## 继续连载

以下完整流程只用于正式入库的连载或修订。用户要求试写接续、审读或局部候选时，使用开头的轻流程，仅取必要前文和事实核对，不执行本节的后处理、审稿与提交事务。

`novella` 同样使用以下读取、写作、后处理、审稿和提交流程，但先读 [novella.md](novella.md)：用全书阶段代替当前卷贯穿线，不按章号安排小/大兑现；一件事完成后，在本次授权范围内沿其后果继续，不因阶段边界自动停笔。全书结局落地或达到本次要求的章节范围时结束任务。

按以下顺序执行，不要依赖聊天记忆代替项目文件：

1. 定位包含 `project.json` 的项目根目录。
2. 若 `schemaVersion` 旧于当前版本，缺少 v6 群像文件、v7 自然度门禁或 v8 重复门禁，先按 [operations.md](operations.md) 运行 `migrate_project.py`。
3. 读取 `canon/story-contract.md`、`canon/style-profile.md`、`canon/publishing-package.md`、`canon/laws.md`、`planning/current-volume.md`、`planning/rolling-outline.md`、`planning/current-arc.md`。
4. 读取 `state/story-state.json`、`state/threads.json`、`state/rewards.json`、`state/cast-arcs.json`、`state/decisions.json`，以及上场角色的 `cast/{id}/state.json`。
5. 读取最近 1–2 章正文、对应审稿报告和最新 `sessions/` 记录；长篇与短中篇先按 [operations.md](operations.md) 的“尾稿保存与跨会话恢复”运行 `draft_checkpoint.py check --project <项目目录>`，优先恢复已写工作尾稿，核对前章最终稿与尾稿的接续。读取 `canon/style-profile.md` 中作者确认的声音证据和适用于本章场景的朱雀候选样本（若存在）。角色状态指向更早的关系转折、未结代价或旧目标时，回查对应正文；只查当前事件需要的前因，不因章界重置关系和情绪。
6. 运行 `validate_project.py`。先处理错误；把警告纳入本章计划。
7. 若存在会阻断本章或当前写作范围的未决重大决策，先给出 2–4 个明确选项及影响，等待作者选择；未来章的判断点不提前阻断当前章。
8. **筹备。** 若无阻断，新事件按 [ensemble.md](ensemble.md) 写合同、按角色知情边界收意图并依法则裁定；同一未完事件跨章先复用有效的前卡、意图与裁定，只有影响选择或合法性的新事实才触发更新。逐章归档不等于逐章重新提案，复制快照的方法见ensemble。先核对当前事件所需的法则、时间线、角色卡与正文，再按任务选读写法参考。短故事或番茄投稿在筹备与编辑阶段核对签约、人物与一致性，开篇另核对信息流入口。按 [writer-context.md](writer-context.md) 选取具体事实、关键意图、相关正文与声音依据，不向写手堆叠课堂全文、诊断清单或机制名称。
9. **连续正文与切片。** 写手先读 [writer-context.md](writer-context.md)，从接续点顺着当前事件写，不接“写一章约2500字”的任务。写的过程中保存草稿并运行 `chapter_cut.py <草稿文件> --target 2500` 实测；`ready` 时按定位的句段边界切开，不等事件、对话或动作结束。切点后的正文留给下一片，按切出的内容后定标题；前片经过后处理、审稿和提交，再从断处继续同一事件。空间、动作、对白、心理按人物注意与回应组织，不预定章内拍数、转折或收尾。短故事仍按已确认分节职责处理。
10. 按 [review-system.md](review-system.md) 运行确定性重复审计、语言风险扫描、[网文自然度强制审稿](webnovel-naturalness-review.md)、编辑审稿和目标读者模拟。自然度审稿对每个新写或修改过的章节都必须执行，不以 lint 通过、普通审稿通过、改动很小或作者催交为跳过理由；命中问题簇时按 [prose-naturalization.md](prose-naturalization.md) 只定向修改证据段，最多自动修改一次，并基于最终正文重新执行全部审稿。
11. 按“章节提交事务”更新全部状态文件，再向作者报告。

**正式入库前的自然度检查：** 第 9 步完成后、第 10 步审稿前，按 [prose-naturalization.md](prose-naturalization.md) 的“正式入库前的自然度检查与定向改稿”执行。范围仅为本次正式入库的新章、分节或授权修订，不含试写和未采用候选。先检查结构、人物选择与接续；有成立问题才在授权范围内处理并保留原稿。语言改写须有原文证据与具体阅读代价，无问题可以原稿进入审稿。实际改写时保存基线、核对事实与声音，记录字数变化；低于原稿90%只触发内容复核，不要求补字或恢复重复。作者要求停止润色时停止改写，正式入库的审稿和哈希绑定仍执行。具体取舍和有限修订轮次按引用章节处理，不重复开启另一套自然化循环。

## 章节提交事务

把正文和状态更新视为同一次提交。不得先直接修改正式项目再补状态：

1. 按 [operations.md](operations.md) 创建 staging 目录，把新正文和所有拟更新文件按项目相对路径写入 staging。
2. 写作时先保存连续正文草稿；切出约2500有效字的一片后，先按operations用 `draft_checkpoint.py save` 保存切片前原稿、前片与尾稿，再按实际内容确定标题，写入 staging 的 `chapters/第NNNN章-标题.md`。未完事件仍留在当前弧与滚动事件纲中，尾后草稿不能提前进入正史。不要覆盖现有章节，除非用户明确要求修订。保存该片原稿到 `reviews/drafts/第NNNN章-before-naturalization.md`，完成后处理并写 `reviews/第NNNN章-naturalization.md`，再运行指标与审稿；报告绑定最终正文。前片提交后先检查保存点，再接续工作尾稿，避免语言或结构改动使尾稿失配。
3. 写作时用 `chapter_cut.py` 定位未切草稿的边界，默认只输出报告。`continue` 表示当前事件继续推进；`ready` 给出 `cutPoint.offset`（原始文本的Unicode字符索引）及两片有效字数；`needs-boundary` 表示附近未找到句段边界，检查已有文本，不改写剧情来适应切点。阈值使用项目的 `targetChapterChars`（默认2500）；`--window` 默认100是自动选点的距离限制，不是写作篇幅合同。事件已经结束时加 `--final` 处理余片。需要导出时同时指定两个新路径，脚本保留原稿与全部尾后文字，拒绝覆盖已有文件：

```bash
python3 <skill-dir>/scripts/chapter_cut.py <连续草稿> --target 2500 --head <当前片新文件> --tail <尾后草稿新文件>
```

   导出两份文件连接后与源文件逐字节相同；标题在切出后添加，尾后草稿不提前进入正史。该操作只用于长篇与短中篇的连续草稿，不能对已确认或已审稿章节重新切分。切片后的字数、段落与语言指标仍由 `chapter_metrics.py` 统计；其中 `lengthSignal` 只为未切草稿服务，`cutPoint` 与切点工具一致。短故事按全文与分节职责处理。

   `fanqie-short-story` 的第一节还要运行 `opening_audit.py <章节文件> --window 300`，并按 [short-story-information-flow.md](short-story-information-flow.md) 完成冷读者复述与编辑因果检查。正文变化后重新运行，不能沿用旧窗口判断。

4. 先运行 `repetition_audit.py`，将结果写入 `reviews/第NNNN章-repetition.json`：番茄短故事比较全部较早已提交分节，长篇默认比较最近 5 章。再运行 `prose_lint.py` 写入 `reviews/第NNNN章-lint.json`，并按 [review-system.md](review-system.md) 分离执行网文自然度审稿、编辑审稿和目标读者模拟，写入 `reviews/第NNNN章-review.json`。番茄短故事的编辑诊断必须按 [fanqie-signing-quality.md](fanqie-signing-quality.md) 与 [fanqie-character-craft.md](fanqie-character-craft.md) 回答空转、人物动机、机制是否运行、胜利代价、情绪是否落到身体、对白是否推进利益而非播报背景、总结句是否替作者或读者下结论、最后一节收口是否做完。第一节与长篇前三章另按 [fanqie-new-book.md](fanqie-new-book.md) 回答设定微创新、首屏看点、无效开篇花活和枯燥句。写章还要按 [fanqie-consistency.md](fanqie-consistency.md) 回答战力/金钱/规则是否对上法则库、时间地点是否接得上、有没有为爽点降智。自然度 finding 必须引用问题簇的逐字证据并说明读者代价；每个保留的 exact/near 重复 finding 都必须有绑定最终正文哈希的 `repetitionExceptions` 和具体编辑理由。不能根据单个词命中机械重写。作者提供朱雀逐段标红时，按 [prose-naturalization.md](prose-naturalization.md) 的段落合同执行：未标红段落原样保留；标红段只允许删除、合并或就地改写，禁止扩成新场面，也禁止改成更短的功能金句段。三份报告与自然度对象都必须绑定当前正文 SHA-256。
5. 若重复、自然度或其他审稿存在阻断项，自动定向修改一次并重新运行指标、重复审计、语言扫描、自然度审稿、编辑审稿和读者模拟。仍有未处置重复、高优先级问题、`needs-revision` 或弃读风险时停止提交；只有符合对应门禁契约的明确例外才可保留。
6. 从已经通过审查的正文抽取新增事实：人物状态、关系变化、时间地点、资源变化、公开信息、秘密揭示、世界规则实例。有时间跳跃、换地点、新伤、新钱或新规则时，同步更新 `canon/timeline.md` 与 `canon/laws.md`。
7. 在 staging 中更新 `state/story-state.json`，不得删除仍然有效的旧事实。
8. 在 staging 中更新 `state/threads.json`：推进、兑现、转化或延期剧情线；延期必须记录原因和新的兑现窗口。
9. 在 staging 中更新 `state/rewards.json`。按 [reward-system.md](reward-system.md) 填写回报类型、铺垫章、正文证据、代价、状态变化和冲突/解法模式，并回答「释放与归属」四问：结果是否由承诺对象挣来、收益有没有被无交换拿走、有没有提前打光终局底牌、旧期待有没有付利息。
10. 在 staging 中更新 `state/cast-arcs.json`：只为本章真实发生的配角选择、人生状态或关系变化追加证据；普通露面不算弧光推进。有人离开当前这段，或到了该回来的时候，同步改他的 `presence`：当前下线但之后还会出现的，写明回到哪条线和哪件事之后；留给后卷或这条线已经说完的，写明卷或原因。同步更新上场角色的 `cast/{id}/state.json`、`contracts/chapter-NNNN.json`、`intents/chapter-NNNN/` 与 `planning/current-arc.md`。弧未闭环则保持 `open`。卡上标明不再出场的人，本章不再写回来。
11. 在 staging 中更新 `planning/rolling-outline.md`：长篇只移除已经真正结束的事件，未完事件沿用原完成条件并更新接续点，不因切出一章就删掉这一段。保持贯穿线起点、必经转折和卷末可见；支流不占章号。兑现记录在实际发生的文本切片中，不按章号补齐15章锚点。短故事删除已完成分节并保留全部剩余结构，不向结局之后补锚点。
12. 在 staging 中更新 `project.json` 的章号、总字数和当前卷；新增 `sessions/` 交接记录。短故事最后一节或短中篇最后一章若要标记 `complete`，同时暂存 `reviews/final-review.json`；短中篇更新 `finiteStory.status`，终审另核对副线、人物归宿和篇幅合同。
13. 运行 `commit_chapter.py --project <项目> --staging <staging>`。它会构造预览项目、校验、备份并提交；不要绕过此步骤。

提交失败时正式项目保持原状态，修复 staging 后重试。若异常中断造成部分写入，使用脚本报告的备份目录执行 `commit_chapter.py --restore`，不得假装提交成功。

## 连续创作多章或多节

本节用于连续正式入库；连续试写仍按轻流程交付候选，未采用文本不提前写入正史。

`novella` 的阶段不按章数分摊，可跨章推进；切章后逐章完成自然度检查、必要的定向改稿、正式审稿和原子提交。实际改稿时复核字数变化与有效叙事，不能借润色补齐章长；作者明确的全书最低字数仍须满足。`finiteStory.status = complete` 后停止自动续写。

- 默认顺着事件连续写作并按实测字数切片。下一片基于已提交正文直接承接，未完事件沿用原完成条件；切章本身不触发重新规划本章剧情。
- 每写完一章都执行完整提交事务，不能等整批结束后才补状态。
- 长篇每推进大约三段贯穿线完成一个小兑现，大约五段完成一个能改变后续局势的大兑现。支流不占这段序，除非它付的是贯穿线的账。大兑现同时执行阶段审查。短故事按结构锚点审查，不为凑章数增写场景。
- 长篇每5章复核核心配角能动性；15章未见核心配角选择或后果时提示检查相关事件与出场安排，不以章号强制新增人物或转折。短故事只保留影响主要矛盾或结局代价的配角选择，不强迫完整副线。
- 到达小篇章或卷末时停止自动跨越边界。贯穿线的卷末状态差落地后，停止写作，不在同一次任务里自动开下一卷。若下一步属于重大决策，先询问作者。
- 不并行撰写相邻正文；相邻章节存在强因果依赖，批量并行容易破坏连续性。

## 长期扩展

使用 [continuation-engine.md](continuation-engine.md) 的扩展闸门。一卷结束后不自动开启下一卷。只有作者要求继续，并且同时满足以下条件，才开启新卷：

- 已兑现至少一个旧承诺；
- 新目标是此前选择或后果导致的，而非凭空降临；
- 规则、关系或代价至少有一项发生结构性变化；
- 至少关闭或转化一条旧剧情线；
- 新冲突的解决方式不能复刻最近两个篇章。

长期连载不等于拒绝结局。始终保留“可收束路径”：当前主线在若干卷内能够结束；如果继续，是开启有因果联系的新阶段，而不是无限拖延同一问题。

## 修订与诊断

先从高层到低层检查：故事承诺 → 卷结构 → 人物弧 → 章节因果 → 场景 → 句子。不要用润色掩盖结构问题。改已有正文前先读 [fanqie-revision.md](fanqie-revision.md)：分清问题类型与范围，能不改就不动；把握不了后文衔接时停止，等作者选择往下写或推倒该段。

修改既有正史前：

1. 列出改动会影响的角色、时间线、伏笔、后续章节和世界规则。
2. 若改动属于重大决策，等待作者确认。连续数章的大剧情、已发表后文会接不上的改动，一律先确认。
3. 大改前把该区间已抛出的设定、伏笔和关键信息记入法则库、时间线与线索账本；重写时填回去。
4. 修改正文与所有受影响状态，记录到 `state/decisions.json`。
5. 运行项目校验，并抽查受影响章节的前后衔接。改开篇时不得把后期人设灌进早期。

用户只指出“AI 味重”“不自然”时，不直接全篇改写。先按 [prose-naturalization.md](prose-naturalization.md) 区分结构问题、人物同声、对白工具化、解释过密、上帝预告、套话反应、标签墙、程序展示过满和主题封口，列出逐字证据与修订范围；保留故事事实和已经成立的个人声音，只对有证据的问题做一次定向修订。

用户提供朱雀 PDF、截图或分段结果时，先读同一文件的“朱雀分段报告的使用”和“从朱雀低 AIGC 片段建立候选声音样本”，核对送检版本、报告哈希与片段范围后再局部处理。最低值片段只有在作者确认读感后，才可作为当前项目的候选声音样本；长篇按章或场景类型调用，不自动覆盖整本书。正式外部证据按 [review-system.md](review-system.md) 保存。复测按文本锚点重新对齐，不按同号片段硬比较；没有新报告就记录未复测。

结构级自然化优先检查四件事：主角的非最优选择是否真正改变后续价格、信任、机会或关系；证据缺口是否改变结论边界，而非最后仍证明主角全面正确；人物声音是否来自不同利益与回避方式；流程删减是否保留了会造成延迟、失败或代价的必要手续。修订后还要对照前后章节和正史，检查叙述者是否在前文把后文仍未知的事实提前说死。

“AI 味分数”只能记录作者或读者的主观感知，不能当作检测结果或持续优化指标。作者明确表示停在当前版本时，把停止条件写入 `canon/style-profile.md` 和 `state/decisions.json`；不得为了继续降分人为增加错误、含混、口语、断句、闲聊或随机障碍。以后只有正常编辑问题或新数据支持的具体假设才重开修订。

## 面向作者的输出

保持简洁，不展示原始 JSON 或内部长清单。

- 写章后以正文为主，简报章节、约略字数、门禁状态及必要的实际变化与未决事项；没有发生的情绪、关系、成长或兑现不逐项汇报。下一步方向需要作者判断时再说明。
- 配角弧光推进时：报告是谁主动做了什么、付出什么代价，以及其目标、能力、身份、信念、关系或立场如何改变。
- 有重大决策时：先说明为什么现在必须决定，再给 2–4 个差异明确的选项和影响。
- 开新书时：正文之前展示终选书名的检索结论、3 个差异明显的书名字效方向及推荐项、适配目标生成器的一次成图提示词、纯底图提示词、标题区域重绘提示词和负面提示词。画面按「画面层」写一种构图和前、中、远三层，只展示入口冲突。不能只交付“书法、大气、金色描边”或“帅气主角加大头贴”之类抽象形容。
- 有校验问题时：区分阻断错误和可继续的警告。
- 不用“无限生成”承诺掩盖上下文限制；依靠项目文件实现跨会话延续。

## 脚本

- `scripts/init_project.py`：创建原创的长篇连载或番茄短故事项目骨架和初始状态。
- `scripts/migrate_project.py`：将旧项目安全迁移到当前 schema，并保留迁移备份。
- `scripts/plan_cadence.py`：长篇只记录贯穿线的兑现间隔，不按章号预排情节；短故事写入全文比例结构锚点。
- `scripts/style_profile.py`：列出、预览或安全应用预设/自定义语言风格档案。
- `scripts/publishing_package.py`：检查书名公式化风险，保存确认书名、公开检索记录和封面提示词。
- `scripts/market_brief.py`：校验并保存带日期、公开来源、样本和置信度的市场观察。
- `scripts/story_overlap.py`：比较候选与历史项目的人名、设定和故事发动机文本信号，提示高同质化风险，不判断抄袭或平台处罚。
- `scripts/reference_guard.py`：比较参考稿与候选正文的连续复用片段和禁用专名，提示编辑风险，不作抄袭或法律认定。
- `scripts/performance_feedback.py`：保存发布后统计窗口，计算阅读/完读漏斗并生成带样本限制的诊断。
- `scripts/commit_chapter.py`：在隔离预览中校验后原子替换文件；失败时自动回滚。
- `scripts/chapter_cut.py`：定位连续草稿的句段切点，可导出当前片和尾后原文。
- `scripts/draft_checkpoint.py`：保存项目内切片与尾稿，按已提交章号恢复；前章或尾稿变化时提示接续核对。
- `scripts/chapter_metrics.py`：统计正文有效字数、段落、对话比例和重复段落信号，并显示同一切点建议。
- `scripts/opening_audit.py`：按有效字符口径截取短故事前 100/200/300 字窗口，输出入口审稿所需的文本与基础指标；不代替语义判断。
- `scripts/merge_chapters.py`：将已提交章节按顺序合并为单一 Markdown，可移除章节 H1，并验证有效字数不变。
- `scripts/prose_lint.py`：扫描模板化语言和项目基线漂移，只输出编辑风险信号。
- `scripts/repetition_audit.py`：检查当前章节内及规定前文范围中的长句精确重复与高相似复述，输出哈希绑定的编辑证据。
- `scripts/validate_project.py`：校验项目结构、JSON 状态、剧情线窗口、爽点正文证据、模式重复、群像合同/意图和提交一致性。
