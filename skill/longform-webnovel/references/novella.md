# 短中篇完整小说

`novella` 是结局预先明确、允许人物与冲突分阶段展开的有限篇幅模式。与番茄短故事相比，它能容纳更长的行动过程、关系变化和后果发酵；与长篇连载相比，它不在主线解决后自动开新卷、换地图或追加反派。

## 建项与篇幅合同

先确认主承诺、主要矛盾、最终选择、不可撤回的代价、人物归宿及结尾类型。参考篇幅可以是 3万–10万有效字，默认目标约 5万字；这些是可调整的创作建议，不是平台投稿门槛。作者指定的范围或下限优先。

项目使用 `project.json.finiteStory`：

```json
{
  "targetTotalChars": 50000,
  "minTotalChars": null,
  "status": "planning",
  "endingType": "closed"
}
```

`targetTotalChars` 是全书目标，不是逐章配额。`minTotalChars` 仅在作者明确要求最低篇幅时填写；完结校验用正文实测总量检查它。`status` 使用 `planning`、`drafting`、`complete`；开放结尾需要作者明确选择，主要行动仍须完成。不设置必须写满的章节数；约 5万字可能分成约 20 章，仅用于工作量估计。

```bash
python3 <skill-dir>/scripts/init_project.py \
  --path <项目目录> --title <书名> --mode novella \
  --style <风格标识> --target-total-chars 50000
```

例如作者要求至少 3万字时另加 `--min-total-chars 30000`。`--sections` 属于番茄短故事，不用于本模式。写第一章前将状态改为 `drafting`。

## 全书终点与阶段

`planning/series-map.md` 保存最终选择、代价、归宿和副线回收；`planning/current-volume.md` 在本模式下保存全书阶段；`planning/rolling-outline.md` 保留剩余阶段，只细化接下来的事件。

阶段通常包括困境与进入、不可逆投入、局势改写、决定性对抗、结局与归宿。它们是因果职责，可以交叠或跨越多章，不按章号和平均字数硬分配。每一阶段记录进入条件、关键选择、真实代价、结束时的状态变化与后续后果。副线只保留会改变主线信息、选择或代价的部分，并注明闭合位置；不要为了篇幅强塞固定数量的副线或人物。

运行 `plan_cadence.py <项目目录> --json` 可查看阶段职责；`--write` 不预写任何章节爽点。已有兑现仍保留，只在其实际发生的章节补入账本。不得套用第 3/5 章兑现或短故事按分节编号分配的比例锚点。

## 连续写作与切章

先写接下来这件事从哪里接起、将发生什么、怎样才结束、服务哪个阶段或副线。沿人物行动及其后果连续写，到 `targetChapterChars`（默认约 2500）附近，在完整句子或动作拍之间切章。切章可以发生在事件中途；下一章承接当时的动作、问题或代价，不重开事件、不复述上一章，也不为了章尾完整提前结案。单次要求只写一章时，在切章处结束该次任务。

阶段是规划单位，事件是推进单位，章是文本切分与提交单位。接近字数只决定切在哪里，不决定剧情必须走到哪里。事情已经完成可以短章；继续多章时，在任务范围内转向它造成的下一件事，不靠补回合、补物件或补手续凑字。全书结局已经落地就停止，不为了目标字数再开剧情；实际不足作者明确下限时，应报告篇幅任务未完成，检查已有冲突的必要展开，不能宣称达标。

每次切章后执行 [prose-naturalization.md](prose-naturalization.md) 的真人感后处理与字数护栏，再按 [review-system.md](review-system.md) 进行重复、语言、自然度、编辑和读者审稿，然后提交正史与状态。重复审计默认比较最近 5 章，与长篇相同。声音档案和作者确认的朱雀候选声音样本按场景调用。

审稿除因果与一致性外，还要检查阶段是否真正改变局势、情绪是否由行动触发、人物是否为选择付价，以及副线是否朝结局汇合。不要把番茄短故事的营销入口或平台签约要求自动当成本模式的通用规则；作者按番茄投稿时再读取对应参考。

## 完结与停止

标记 `finiteStory.status = complete` 前，必须完成以下事项：

- 主承诺兑现，主要行动完成，结局代价与人物归宿可见；主要副线闭合。
- 所有线程为 `resolved` 或 `transformed`；开放结尾保留的次级未知应明确转化为已确认的余韵，不能遗留主线欠账。
- 最后一章记录已交付的 `major` 结局回报，实际字数满足作者明确下限。
- 按章号顺序通读全文，生成绑定全部已提交章文件名和正文哈希的 `reviews/final-review.json`，与最后一章一起暂存提交。

终审复用 [review-system.md](review-system.md) 的全文结构，将 `storyMode` 写为 `novella`，`checks` 在通用七项之外增加 `subplots`、`characterDestinations`、`lengthContract`，均须为 `pass`。下限与结局回报由校验器检查；文学判断由审稿记录承担，脚本通过不证明小说质量。

目标总字数与明确下限分开：仅低于目标的九成会提示复核，低于明确下限会阻断完结。不得为消除提示注水。完结章号可以不同于任何估算，不能要求刚好写满 20 章。完结后停止自动续写；修改已有正文使用 `--allow-revision` 并更新终审，新续作或改模式需重新确认合同。

这是 v8 的新增可选模式。旧 `serial` 与 `fanqie-short-story` 项目保持原字段和行为，迁移工具不自动改变作品模式；明确改为短中篇时才更新合同、规划、`storyMode` 与 `finiteStory`，并重新校验。
