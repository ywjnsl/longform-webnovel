# 爽点账本、长篇节拍与短故事锚点

## 贯穿线段序

本节仅适用于 `serial`。兑现按贯穿线已经推进的段数计算，不按全书章号。`fanqie-short-story` 不执行这段序，改按 [length-modes.md](length-modes.md) 的全文比例结构定位回报。

支流段不计入下面的段序，也不占用兑现位置。只有这段支流付的就是贯穿线上的那笔账时，才把这一段算进去，并在 beat 上写明 `paysSpine: true`。没有这句的支流兑现，只算支流自己的结果。

| 贯穿线段序 | 作用 | 最低回报 |
|---:|---|---|
| 1 | 起势，建立当轮目标 | 普通推进 |
| 2 | 加压，制造明确缺口 | 普通推进 |
| 3 | 第一次小兑现 | `small` |
| 4 | 扩大代价，为大兑现蓄力 | 普通推进 |
| 5 | 第一次阶段大兑现 | `major` |
| 6 | 承接胜利余波，交付新筹码或关系收益 | `small` |
| 7 | 打开由旧后果导致的新局面 | 普通推进 |
| 8 | 二次加压 | 普通推进 |
| 9 | 第二次小兑现 | `small` |
| 10 | 第二次阶段大兑现 | `major` |
| 11 | 让角色承担胜利后果 | 普通推进 |
| 12 | 第三次小兑现 | `small` |
| 13 | 多线汇合 | 普通推进 |
| 14 | 高潮蓄力，锁定不可回避的选择 | 普通推进 |
| 15 | 这一轮的大兑现，同时吸收小兑现职责 | `major` |

段序数到 15 之后从头再计，仍然只数贯穿线。紧跟大兑现的那次小兑现优先交付战利品、认可、关系主动权或新情报，不连续安排同类高潮。一卷的最后一段是贯穿线落地，由它交付本卷的大兑现。

`project.json.rewardCadence` 里的 `smallEvery: 3` 和 `majorEvery: 5` 表示贯穿线段序，不是文件章号。不要因为全书第 3 章或第 5 章到了，就把兑现挪到支流上。

## Beat 结构

`state/rewards.json` 中的 `beats` 使用以下字段：

```json
{
  "chapter": 5,
  "level": "major",
  "status": "delivered",
  "role": "第一次阶段大兑现",
  "rewardType": "truth",
  "payoff": "主角公开证据，洗清嫌疑并锁定幕后组织",
  "setupChapters": [1, 2, 4],
  "evidence": ["投影幕布上，转账记录与录音时间严丝合缝。"],
  "cost": "幕后组织转而威胁主角家人",
  "stateDeltas": ["主角恢复公开身份", "对手从观察转为追杀"],
  "sourceThreadIds": ["main-framed"],
  "conflictType": "public-accusation",
  "solutionType": "evidence-exposure"
}
```

## 字段规则

- `status` 使用 `planned`、`delivered` 或迁移专用的 `needs-review`。
- `rewardType` 使用 `power`、`status`、`relationship`、`truth`、`resource`、`revenge`、`emotional`、`escape`、`achievement`、`other`；未完成计划可暂用 `unassigned`。
- `setupChapters` 只列当前章之前真正承担铺垫功能的章节。
- `evidence` 在兑现后保存正文中 6–120 字的原文片段；校验器会确认片段确实存在于对应章节。
- `cost` 说明回报带来的代价、新责任或新约束。`major` 必须有具体代价。
- `stateDeltas` 写结果，不写感受；`small` 至少一项，`major` 至少两项。
- `sourceThreadIds` 关联被推进、兑现或转化的剧情线。大爽点通常至少关联一条。
- `conflictType` 与 `solutionType` 使用稳定、简短的描述，用于检测重复模式。

## 计划与兑现

规划时先用 `plan_cadence.py` 核对贯穿线的兑现间隔。它不为未来章号预先写入兑现锚点。真正要兑现时，把这一章的 beat 写进 `state/rewards.json`。长篇普通推进、短故事非锚点分节也必须有推进或回报，但不必写入节拍账本。支流章的 beat 若 `lane` 为 `side` 且没有 `paysSpine: true`，不计入贯穿线段序。

兑现后必须从最终正文提取证据，再把状态改成 `delivered`。不得先把账本写成已兑现，再去凑正文。

## 释放与归属

规划或核对一次兑现时，先回答四句。答不上来就改回报设计，不靠加一场旁观惊叹补强度：

- 这个结果是不是承诺对象的选择挣来的？群像、导师、制度合作题材可以事先把高光许给别人；个人逆袭题材不能让路过的强者或机构无交换地收走。
- 核心收益有没有被配角、巧合或上级无交换拿走？必须交出去时，要换到看得见的权力、保护、渠道或下一步行动权。
- 这一拍有没有提前打光终局底牌：头号对手结案、终极身世揭完、金手指到顶、感情最终定局？阶段性胜利可以一战多得，但不能把后面的台阶用完。
- 旧期待有没有付一点利息？新地图、新势力、新谜团不能用来逃避还没动的旧承诺。

铺垫拉得越高，亮出底牌后的压制就要越清楚。亮了牌、对手毫无损失、主角再被无代价打回去，这次兑现失败。高潮后的下一章可以先交付战利品、认可或关系收益，不必立刻再加压。

连续两个同级爽点不得复用完全相同的 `conflictType + solutionType + rewardType`。连续三个同级爽点使用相同 `rewardType` 会触发疲劳警告。
